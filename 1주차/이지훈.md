1. msw 가 무엇인가

[**MSW(Mock Service Worker)**](https://mswjs.io/docs/)는 Service Worker를 이용해 서버를 향한 실제 네트워크 요청을 가로채서(intercept) 모의 응답 (Mocked response)를 보내주는 API Mocking 라이브러리이다. 

MSW를 사용하면 직접 Mock 서버를 구현하지 않아도, 네트워크 수준에서 API를 Mocking 할 수 있다.

MSW의 주요 특징은 아래와 같다.

- Mocking 테스트를 위한 노드(node.js)환경, 개발 및 디버깅을 위한 브라우저 환경에서 모두 사용할 수 있다.

- 소스 코드 수정 없이 모킹이 필요한 환경에서만 MSW 인스턴스를 실행해 API Mocking을 적용할 수 있다.

- 어플리케이션 레벨이 아닌 네트워크 레벨에서 요청을 가로채기 때문에, 모든 종류의 네트워크 라이브러리(axios, react-query 등) 및 네이티브 fetch 메서드와 함께 사용할 수 있다.

- Service Worker를 통해 실제 HTTP 요청을 흉내내기 때문에, 실제 API를 사용할 때와 동일한 방식으로 개발이 가능하다.

- 백엔드 API가 완성되기 전에도 프론트엔드 개발을 진행할 수 있어 개발 병목 현상을 줄일 수 있다.

2. 왜 사용하는가? 목데이터 만들어서 하면되는데

대부분 어플리케이션 내부 로직에 직접 모킹해서 해결한다. 하지만 이 방법은 서비스 로직을 직접 수정해야하고, HTTP 메서드 응답을 상태별로 대응하기 어렵고, 조금만 관리가 소홀해도 테스트코드와 실제 코드가 섞여 유지보수가 어려워질 수 있다.

이 다음 선택지는 네이티브 모듈을 바꿔치는 선택을 하게된다. 이 방법을 사용하면 간단한 단위 테스트에서는 문제가 없겠지만 실제 환경과 차이점이 발생해 end-to-end 테스트에서 문제가 발생할 수 있다. 가장 중요한 브라우저와 node 환경에서 다르게 동작하는 것도 큰 문제가 될 수 있다

마지막으로 MSW를 사용하지 않고, 모킹 서버를 직접 구현하려한다. 하지만 많은 리소스가 필요하지만 부족해 절망을 느낄 수 있다. 또한 실제 서버와 동작 방식이 달라 별도의 코드 수정을 통한 시간 소비가 발생한다.

이런 이유들 때문에 간단한 설정이 있는 컴포넌트 단위에서는 직접 목데이터를 만들어서 사용하지만, 확장성이 커질수록 다른 접근을 해야한다. 나는 이런 선택을 MSW로 해결했다.

3. 진짜 마지막으로 MSW 말고 다른 라이브러리으로 대체할 수 없어? 

axios-mock-adapter](https://github.com/ctimmerm/axios-mock-adapter)나[nock](https://github.com/nock/nock)같은 API 통신을 모의하는 라이브러리를 고민해볼 수 있다.

axios-mock-adapter는 axios를 사용하는 프로젝트에서 사용할 수 있는 라이브러리로, axios의 인스턴스를 생성하고 해당 인스턴스에 대해 Mocking을 적용할 수 있다.

한계점이라면 다른 HTTP 클라이언트에서 확장해 사용할 수 없고, 브라우저 환경에서만 동작하기에 시뮬레이션해보기 어렵다. 그렇기에 인스턴스를 직접 수정해야하는데 위험이 크다.

다음 선택지는 nock 라이브러리이다. nock는 Node.js 환경에서 사용할 수 있는 HTTP 요청 Mocking 라이브러리로, HTTP 요청을 가로채서 Mocking을 적용할 수 있다.

이 라이브러리는 Node.js 환경에서만 사용할 수 있기 때문에 브라우저 환경에서는 사용할 수 없다. 또한, nock를 사용하면 실제 HTTP 요청을 가로채기 때문에, 실제 서버와의 통신이 불가능하다.

네트워크 동작의 차이점이 발생하기에 MSW를 대체할 수 없다고 생각한다.

4. 그래서 MSW를 사용해야하는가? 그럼 장점이 뭔데?

위에서 다른 선택지들을 통해 발생하는 문제점을 살펴보았다. 이런 문제들이 있기에 MSW의 장점이 더 크게 느껴진다.

통합된 테스트 환경을 제공해 브라우저, node.js 환경 모두 지원하고 HTTP 클라이언트 라이브러리와 쉽게 사용할 수 있다.

또한 서비스 로직 수정 없이 모킹이 가능하고, 테스트 코드와 명확히 분리해 가독성이 좋아진다. 가장 큰 장점으로 Service Worker을 통해 네트워크 레벨 요청을 가로채 실제 API와 가까운 시물레이션을 할 수 있다. 그래서 end-to-end 테스트에서도 신뢰성있는 결과를 만들어준다.

5. 사용하면 어떤 상황에 쓰는게 좋을까?

백앤드 API 스펙이 없을떄? 개발 지연 될 때? 테스트 코드 작성이 어려울 때? 이런 상황에서 MSW를 사용하면 좋다. 

나는 QA 전 다양한 시나리오를 만들어 테스트할 때 사용한다.

이 글을 보고 있는 분들을 위해 **[간단하게 구현해보았으니](https://github.com/sipe-team/3-2_tdd-bdd/tree/jihoon-msw-sample)** 확인해보면 좋겠다. 


6. v1 ⇒ v2로 변경된 부분이 많아보이는데 어떤게 중점적으로 바뀌었을까

Handler 네임스페이스가 변경되었다.

기존 rest를 http로 네임스페이스 변경했고, 응답 형식이 더 표준화된 방식으로 변경되었다. 간혹 AI를 활용해 개발할 때 rest로 안내해주는 경우가 있으니 인지하길 바란다.

```ts
// v1
import { rest } from 'msw'
rest.get('/api/users', (req, res, ctx) => {
  return res(ctx.json({ users: [] }))
})

// v2
import { http } from 'msw'
http.get('/api/users', () => {
  return HttpResponse.json({ users: [] })
})
```

<br/>

응답 구조 변경되었다. 

res()와 ctx 유틸리티 제거되었고, 웹 표준인 Response 객체 기반으로 변경되었다.

```ts
// / v1
rest.get('/api', (req, res, ctx) => {
  return res(
    ctx.status(200),
    ctx.json({ data: 'value' })
  )
})

// v2
http.get('/api', () => {
  return new HttpResponse(
    JSON.stringify({ data: 'value' }), 
    { status: 200 }
  )
  // 또는 더 간단하게
  return HttpResponse.json({ data: 'value' })
})
```

<br/>

요청 정보 접근 방식을 단일 객체로 통합해 구조화를 진행했다.

```ts
// v1
rest.get('/api/:id', (req, res, ctx) => {
  const { id } = req.params
  const query = req.url.searchParams.get('query')
})

// v2
http.get('/api/:id', ({ params, request }) => {
  const { id } = params
  const url = new URL(request.url)
  const query = url.searchParams.get('query')
})
```

<br/>

환경별 명확한 임포트 경로 구분해 브라우저/노드 환경 분리했다.

```ts
// v1
import { setupWorker } from 'msw'

// v2
import { setupWorker } from 'msw/browser'
// 또는
import { setupServer } from 'msw/node'

```

<br/>

지연 처리 방식을 변경했다.

```ts
// v1
rest.get('/api', (req, res, ctx) => {
  return res(ctx.delay(1000), ctx.json({}))
})

// v2
http.get('/api', async () => {
  await delay(1000)
  return HttpResponse.json({})
})

```

마지막으로 환경 요구사항이 바뀌었는데 Node.js 18.0.0 이상, TS 4.7 이상, Response/Request/TextEncoder API 지원이 필요하다.

7.  생각하는 MSW 의 주요 메서드에 몇개를 선정해보자


공식문서에 자세하게 나와있으니, 내가 개발을 진행하면서 신경써서 살펴본 메서드들을 알아보자.

- [HttpResponse](https://mswjs.io/docs/api/http-response)는 HTTP 응답을 생성하는 메서드이다.

- [delay()](https://mswjs.io/docs/api/delay) : 네트워크 지연 시뮬레이션

- 실제 네트워크 요청 허용하는 [bypass(https://mswjs.io/docs/api/bypass)] 메서드도 중요하다.

마지막으로 msw 에서 제공하는 setupWorker/setupServer(MSW 설정 메서드)가 제일 중요하다... 꼭 읽어보라!!!
