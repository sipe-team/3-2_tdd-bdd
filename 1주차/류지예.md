# 모킹이란 무엇인가

## 1. 테스트 대역과 모킹

### 1.1 테스트 대역의 이해

[테스트 대역(Test Double)](https://martinfowler.com/bliki/TestDouble.html)
- Gerard Meszaros가 2007년 그의 저서 "xUnit Test Patterns"에서 처음 체계화
- 영화의 스턴트 대역(stunt double)에서 착안
- 테스트에서 실제 객체 대신 사용되는 모든 종류의 가짜 객체를 일컫는 포괄적인 용어

```plaintext
[테스트 대역의 분류]
Dummy → 단순 파라미터 채우기
        (인터페이스 만족)
Mock  → 행위 검증이 주 목적
        (함수 호출, 인자, 호출 순서 등)
Stub  → 미리 준비된 응답 제공
        (특정 상태나 시나리오 테스트)
Spy   → 호출 정보 기록
        (함수 호출 여부와 방식 추적)
Fake  → 실제 구현 단순화
        (가벼운 대체 구현)
```


<details>
  <summary>실제 코드 예시와 설명</summary>

  **1. Dummy**
  ```typescript
  // 테스트에서 실제로 사용되지 않는 인자가 필요할 때
  const dummyUser = { id: null, name: null };
  ```

  **2. Stub**
  ```typescript
    // 특정 상태나 시나리오를 테스트할 때
  const stubUserAPI = {
    getUser: () => ({ id: 1, name: 'Test' })
  };
  ```

  **3. Spy**
  ```typescript
  // 함수나 이벤트 핸들러가 정상적으로 호출되었는지 검증할 때
  const spy = jest.spyOn(user, 'save');
  // - 함수가 정상적으로 호출되었는지 검증할 때
  // - 이벤트 핸들러의 호출을 추적할 때
  ```

  **4. Mock**
  ```typescript
  // API 응답이나 복잡한 객체의 동작을 시뮬레이션할 때
  const mockUserService = jest.fn().mockImplementation(() => {
    return { validate: () => true };
  });
  ```

  **5. Fake**
  ```typescript
  // 실제 구현을 단순화한 가벼운 대체 구현
  class FakeUserService {
    validate() {
      return true;
    }
  }
  ```
</details>

### 1.2 모킹의 특별한 위치

모킹이 다른 테스트 대역과 구분되는 핵심은 '**행위 검증**'

```typescript
// 예시: 결제 시스템 테스트

// Stub 방식: 결과만 확인
const stubPayment = {
  process: () => ({ success: true })
};
// 결제가 성공했는지만 확인

// Mock 방식: 행동 검증
const mockPayment = jest.fn();
// 정확한 금액이 전달되었는지
expect(mockPayment).toHaveBeenCalledWith(1000);
// 한 번만 호출되었는지
expect(mockPayment).toHaveBeenCalledTimes(1);
```

- 이러한 모킹의 특성은 현대 프론트엔드 개발에서 더욱 중요해짐
  - → API 통신, 사용자 이벤트 처리 등 외부 의존성이 많은 환경
  - → 효과적인 모킹 전략 필수적

## 2. 프론트엔드 테스팅의 도전과 변화

### 2.1 모킹 도구의 진화

```plaintext
[모킹 도구의 진화]
수동 모킹      → Jest 자동 모킹    → MSW
(함수 단위)      (모듈 단위)        (네트워크 단위)
```

1. 수동 모킹의 번거로움
2. 사용자 관점의 테스트 부족
3. 실제 API와의 차이

→ 이러한 고민들을 해결하기 위해 모킹 도구들이 발전해왔습니다

### 2.3 Jest의 모킹 철학

- Jest
  - 모킹을 자동화하여 개발자의 부담을 크게 줄임
  - 모듈 단위의 자동 모킹의 경우 테스트 작성 시간을 크게 단축

    ```typescript
    // 1. 자동 모킹: 모듈 전체를 자동으로 모킹
    jest.mock('./userService');
    // - 개발자의 수고 감소
    // - 빠른 테스트 작성

    // 2. 선택적 모킹: 실제 구현과 모킹의 혼합
    jest.mock('./userService', () => {
      const actual = jest.requireActual('./userService');
      return {
        ...actual,
        getUser: jest.fn()
      };
    });
    // - 더 현실적인 테스트 환경
    // - 필요한 부분만 모킹
    ```

### 2.4 RTL의 모킹 철학

- React Testing Library
  - "사용자가 애플리케이션을 어떻게 사용하는가"에 초점
  - 모킹에도 영향을 주어, 단순히 함수를 모킹하는 것을 넘어 사용자 관점의 테스트 환경을 구성하는 것이 중요해짐

    ```typescript
    // 1. 사용자 관점의 테스트
    const { getByText } = render(<App />);
    expect(getByText('Hello')).toBeInTheDocument();
    // - 실제 사용자 경험에 집중
    // - 구현 세부사항에 대한 테스트 자제

    // 2. 구현 세부사항 테스트
    const { getByText } = render(<App />);
    expect(getByText('Hello')).toBeInTheDocument();
    // - 구현 세부사항에 대한 테스트
    // - 사용자 관점의 테스트와 병행
    ```

## 3. MSW의 등장과 모킹의 새로운 패러다임

### 3.1 MSW: 새로운 모킹 패러다임

MSW의 등장은 테스트 대역 활용에 새로운 관점을 제시했습니다.

- 기존 : 함수/모듈 단위 모킹
  - 격리된 테스트, 구현 의존적, 깨지기 쉬운 테스트
- MSW : **네트워크 수준 모킹**
  - 실제 환경과 유사, 구현 독립적, 견고한 테스트

### 3.2 MSW의 특징

```typescript
// Service Worker를 통한 실제 네트워크 요청 가로채기
rest.get('/api/user', (req, res, ctx) => {
  return res(
    ctx.delay(500), // 실제 네트워크 지연 시뮬레이션
    ctx.status(200), // HTTP 상태
    ctx.json({ name: 'John' }) // 응답 데이터
  );
});
```
- 실제 API와 동일한 동작
- 프론트엔드 개발 생산성 향상
- 네트워크 에러 상황 테스트 용이
